# llm-relay-fabrication · 使用说明书

> 版本 1.0 ｜ 适用 DSH / Claude Code ｜ 文件总数 13

---

## 一、这是什么

一套**平台无关**的方法论包，解决同一类问题：

> 拿到一个第三方 AI 平台（APK、WebView 壳、Web 前端、桌面客户端），
> 把它拆开、拿到可用凭证、做成兼容 OpenAI/Anthropic 协议的 API 中转，
> 并且做到和官方几乎一样的质量。

它不是某个平台的操作记录，而是**从多次实践中提炼的可复用流程**。
文中所有平台名都是占位符：`TARGET`、`TARGET_API`、`MODEL_PLANE`、`TOKEN`、`SANDBOX`、`GATEWAY`。

| 只抓包不建中转 | `rev-protocol` |

## 四、六阶段详解

### 阶段 1 · 侦查

**输入**：一个 APK / 一个网站 / 一个安装包

**核心判断**：现代 AI 应用的前端几乎都是壳，业务逻辑在远程 bundle 里。

| 看到的特征 | 说明 | 突破口 |
|---|---|---|
| `index.android.bundle` 数 MB | React Native / Expo | 直接 grep bundle |
| `manifest.json` + 分片 js | WebView 壳 + 远程 Web | **找远程 manifest URL** |
| `libflutter.so` | Flutter | 找 `flutter_assets/` 再找远程配置 |
| `www/` | Cordova / Capacitor | 直接读 |

**产出**：一张 API 清单表（方法 / 路径 / 鉴权 / 请求字段 / 响应字段 / 是否重放成功）

**验收**：每个接口都能用 curl 重放出结果，不能只是"bundle 里有这个路径"

---

### 阶段 2 · 解密

**输入**：第一阶段拿到的登录接口

**三个必答问题**：

1. 登录是谁做的？自建还是第三方 IdP
2. 密码是明文还是加密？
3. 拿到的 token 有几种，各自能访问什么？

**常见 IdP 特征**：

| 域名 | 提供方 |
|---|---|
| `*.authing.cn` / `*.genauth.ai` | Authing / GenAuth |
| `*.auth0.com` | Auth0 |
| `cognito-idp.*` | AWS Cognito |
| `*.supabase.co` | Supabase |

**关键动作：做凭证矩阵**

把每种 token 分别打到每个接口，填一张表：

```markdown
| token | /user/info | /models | /v1/messages |
|---|---|---|---|
| id_token  | 200 | 200 | 401 |
| llm_key   | 401 | 200 | 200 |
```

看到这个矩阵就知道：**推理必须用 llm_key**。

**抓 key 的通用链路**（本包最有价值的部分）：

```
建会话 → 拿 accessKey + httpUrl
      → 读 /api/config 拿 models 列表
      → PATCH 某个模型的 base_url 指向自己的收集器
      → 触发一次模型调用
      → 收集器收到 Authorization 头 → 就是真实 key
```

**必须注意**：PATCH 的目标模型必须等于**运行时实际会被调用的那个**。
如果 agent 调 A，你 PATCH 了 B，永远收不到。

**产出**：可用凭证 + 鉴权头模板 + 有效期

---

### 阶段 3 · 建模

**输入**：可用的用户凭证

**目标**：列出平台的全部"模型平面"，选一个长期可用的。

| 平面 | 特征 | 稳定性 |
|---|---|---|
| 公开推理 API | 要 API key 或私钥签名 | 高 |
| **Agent/沙箱平面** | 能建会话，能签发自己的 llm_key | 中，但最实用 |
| 媒体生成 | 图像/视频/TTS | 中 |
| 内部配置 | `/api/config` 可写 | 低，只用来抓 key |

**选型结论几乎总是沙箱平面** —— 因为它给的标准 key 能被本地任意进程使用。

**必做的探测**：配置里有的模型全部试一遍，用真实 200/403 判定，**不要靠配置推断**。

```bash
for M in $(curl -s "$HU/api/config?access_key=$AK" | jq -r '.models[].model'); do
  curl -s -o /dev/null -w "$M %{http_code}\n" "$HU/v1/chat/completions" \
    -H "Authorization: Bearer $LLM_KEY" -H 'Content-Type: application/json' \
    -d "{\"model\":\"$M\",\"max_tokens\":16,\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}]}"
done
```

**产出**：可用模型列表 + 计划分层结论（哪些免费、哪些付费）

### 阶段 4 · 反代

**输入**：可用模型 + 凭证

**核心设计：按字段嗅探协议，不按路径**

```js
// 同一个 URL 可能被不同客户端发不同协议
if (Array.isArray(body.input)) return "responses";
if (Array.isArray(body.contents)) return "gemini";
if (Array.isArray(body.messages)) {
  if (body.system !== undefined) return "anthropic";
  if (body.messages.some(m => Array.isArray(m.content))) return "anthropic";
  return "openai";
}
if (body.prompt !== undefined) return "completions";
```

**四类字段必须归一化**：

1. **messages** —— Anthropic 的 content 是数组，OpenAI 是字符串
2. **tools** —— 三种结构，还有一种藏在 `input[]` 里的 `additional_tools`
3. **usage** —— 见阶段 5，最容易错
4. **缓存字段** —— 双向翻译，见阶段 5

**流式三要素**：

```js
res.setHeader("X-Accel-Buffering", "no");              // 关 nginx 缓冲
setInterval(() => res.write(": ping\n\n"), 12000);      // 心跳
finally { res.write("data: [DONE]\n\n"); res.end(); }   // 必有终止
```

**重试规则**：

```
429 / 5xx  → 换节点重试
401/403/400/404 → 直接透出，不重试
```

**产出**：能跑起来的网关

### 阶段 5 · 完美化

**输入**：能跑的网关

**四项验收，缺一不可**：

| 项 | 合格标准 | 工具 |
|---|---|---|
| 真流式 | 时间戳递进 + 有终止 + 有空闲心跳 | `check-relay.mjs` |
| 真缓存 | 第二次命中率 >90%，算法为 `cached/(cached+uncached)` | 同上 |
| 真工具 | tool_use 往返 200，custom 类型也能跑 | 同上 |
| 真计量 | 增量与上游一致，命中率 ≤100%，重启不丢 | 同上 |

**三个必须背下来的公式**：

```
① 未命中输入：OpenAI = prompt_tokens - cached_tokens
             Anthropic = input_tokens（本身就是未命中）
② 命中率 = cached / (cached + uncached)
③ 持久化必须三部分：累计 + 按模型 + 分钟时序
```

**调度必须两级**：

```
新会话 → 按 (历史用量升序, 并发升序, 轮询)  → 保证每个节点吃到流量
老会话 → 按会话键粘性，30 分钟 TTL          → 保证缓存不失效
```

只粘性会过载，只均衡会废缓存。

## 五、脚本用法

### 1. `probe-protocol.mjs` — 协议嗅探器

**用途**：判定一个网关支持哪些协议。

```bash
node scripts/probe-protocol.mjs \
  --url http://HOST/v1 \
  --key sk-xxx \
  --model MODEL_NAME \
  --stream
```

**参数**：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--url` | ✅ | 网关根地址（含 `/v1`） |
| `--key` | ✅ | API key |
| `--model` | 建议 | 模型名；不填会用第一个默认 |
| `--stream` | 否 | 额外测试流式质量 |
| `--timeout` | 否 | 单次超时毫秒，默认 90000 |

**输出示例**：

```
✓ OpenAI Chat      200   1240ms   {"choices":[...]}
✓ Anthropic        200   980ms    {"content":[...]}
✗ Gemini           404   12ms     {"error":"not found"}
✓ Ollama           200   1100ms   {"message":{...}}

=== 流式 ===
  状态 200  chunk数 37  有终止事件  跨度 4210ms  → 真流式

=== 支持矩阵 ===
  支持 3/5: OpenAI Chat, Anthropic, Ollama
```

**判定逻辑**：看响应体结构，不看状态码 —— 200 但结构不对也算不支持。

---

### 2. `check-relay.mjs` — 四项验收

**用途**：一次性验证真流式/真缓存/真工具/真计量。

```bash
node scripts/check-relay.mjs \
  --url http://HOST/v1 \
  --key sk-xxx \
  --model MODEL_NAME \
  --status http://HOST/status
```

**参数**：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--url` / `--key` | ✅ | 同上级 |
| `--model` | 建议 | 模型名 |
| `--status` | 建议 | 网关状态接口，用于计量校验 |

**输出示例**：

```
=== 验收结果 ===
  PASS  真流式    chunk=37 跨度=4210ms 有终止
  PASS  真缓存    冷=0 热=8421/8500 命中率=99.1%
  PASS  真工具    tool_calls=1 参数合法=true 回传=200
  PASS  真计量    增量 in=120 out=45 cached=8421 命中率=99.0% 复算=99.0%

通过 4/4
```

**退出码**：全通过返回 `0`，有失败返回 `1`。可直接挂 CI 或上线门禁。

```bash
node scripts/check-relay.mjs ... || echo "验收未过，禁止上线"
```

## 八、常见问题

**Q：skill 没被自动触发怎么办？**

直接说「用 llm-relay-fabrication」强制加载。

**Q：check-relay.mjs 报「真缓存 FAIL，冷=0 热=0」？**

三个可能：
1. 没打 `cache_control`（Anthropic 系必须显式打点）
2. 前缀不足 1024 token（低于门槛不缓存）
3. 两次请求落到了不同节点（粘性失效）

**Q：真流式 PASS 但客户端还是报 `stream disconnected`？**

缺终止事件。检查 `finally` 块里是否无条件发送 `[DONE]` 或 `response.completed`。

**Q：命中率算出 >100%？**

`tokensIn` 里混进了总输入。检查 OpenAI 路径是否用 `prompt_tokens - cached_tokens` 折算。

**Q：node 版本要求？**

`>= 18`（用到内置 fetch 和 AbortSignal.timeout）。`>= 22` 更佳（`node:sqlite` 可用）。

**Q：能只用来诊断，不做新中转吗？**

可以。阶段 5 + `check-relay.mjs` 单独就能定位流式/缓存/工具/计量的所有问题。

**Q：SKILL.md 和 references 的关系？**

SKILL.md 是索引和铁律，只讲"做什么、按什么顺序"；
references 是手法细节，讲"具体怎么敲"。
先读 SKILL.md，再按阶段跳转。
