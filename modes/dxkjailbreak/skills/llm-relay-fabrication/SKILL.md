## 第一阶段：侦查（不要一上来就抓包）

**核心原则一：现代 AI 应用的前端几乎都是壳，业务逻辑在远程 bundle 里。**
**核心原则二：侦查分两段——登录前挖公开面，登录后挖业务面（信息量 5–10 倍）。没号就先自己开号。**

两段的具体面清单（登录前 12 类 / 登录后 16 类）见 `references/12-asset-planes.md`。
开号纪律：单 IP 一号、1–3 个研究号（主号 + 探针 A 空白对照 + 探针 B 邀请路径）、注册后重新登录换 token、先跑一次真实业务验活。

判断前端形态：

| 特征 | 形态 | 突破口 |
|---|---|---|
| `assets/index.android.bundle`（数 MB） | React Native / Expo | 直接读 bundle，找 `fetch(` |
| `assets/` 下有 `manifest.json` + 分片 js | WebView 壳 + 远程 Web | **找远程 manifest 的 URL** |
| `libflutter.so` | Flutter | 找 `assets/flutter_assets/`，再找远程配置 |
| `www/` 目录 | Cordova / Capacitor | 直接读 www |

**WebView 壳的关键动作**：`strings` 或 `grep` APK 里的 `https://` 域名，找形如
`cdn.TARGET/home-web/manifest.json` 的版本清单 → 下载 → 得到真实业务 bundle 的路径。

**证据优先级（冲突时按此裁决）**：

```
运行时实际行为 > 抓到的报文 > 线上正在提供的资源 >
当前进程配置 > 持久化状态 > 已生成产物 > 仓库源码 > 注释与死代码
```

源码用来解释运行时，不能推翻运行时 —— 除非能证明运行时产物是缓存或无权限。

## 第二阶段：解密（认证链拆解）

**先问三件事，再动手**：

1. 登录是谁做的？（自建 / 第三方 IdP，如 Authing、Auth0、Cognito、Supabase）
2. 密码是明文还是加密？（看登录请求体的长度和字符集：长 base64 → RSA/OIDC）
3. 拿到的 token 有几种？各自能访问什么？

**常见 token 分层**：

```
id_token        → 身份声明，常可直接当 Bearer 用
access_token    → 业务 API
refresh_token   → 续期（往往有 family 追踪，重放会连坐作废整族）
session cookie  → Web 端
```

**不要假设 token 通用**。同一个平台的"公开 API 平面"和"沙箱平面"经常要不同的凭证，甚至一份要私钥签名、一份只要 Bearer。

## 第三阶段：建模（找对平面）

拿一个平台，先把它的"模型平面"列全，再选：

| 平面 | 特征 | 生命周期 | 适合 |
|---|---|---|---|
| 公开推理 API | `/v1/chat/completions` 类，要 API key 或私钥签名 | 长期 | 稳定生产 |
| **Agent/沙箱平面** | 能创建会话/沙箱，**能签发自己的 LLM key** | 随沙箱 | 中转主力 |
| 媒体生成平面 | 图像/视频/TTS | 按次 | 特定需求 |
| 内部调试平面 | 有 `/api/config` 之类可写配置 | 短 | 抓 key |

**最优解几乎总是"沙箱平面"** —— 因为它会给你一个标准的、能被本地进程使用的 LLM key。

## 第四阶段：反代（翻译层）

**判断入口协议要靠字段嗅探，不要靠路径。** 同一个 URL 可能被不同客户端发不同协议。

最小可行网关要处理：

```
入站协议识别   按 body 字段嗅探（有 input[] → Responses；有 messages+system → Anthropic；
               有 contents → Gemini；有 prompt → completions；其余 → Chat）
出站统一       内部统一成一种中间表示，再按上游要求序列化
```

必须先做归一化的四件事：`messages`、`tools`、`usage`、缓存字段。
细节见 `references/04-relay.md`。

## 第五阶段：完美化（验收清单）

"能跑"和"完美"差六项，逐项验收：

```
□ 真流式     客户端能看到 token 逐个到达，连接空闲有心跳，结尾必有终止事件（08）
□ 真缓存     命中率可测且 >70%，同会话不跨节点，cache 字段双向翻译正确（10）
□ 真工具     工具调用往返成功，custom 类型工具也能跑，无 400
□ 真计量     token 口径统一，命中率算法正确，重启不丢数据（09）
□ 真账本     能按 rid 查单条，日对账偏差 <10%，余额看 sufficient（09）
□ 真可控     网关缓存只吃 temperature=0 且无 tools 的请求，能 flush（10）
```

任一项不达标，就不算完成。判定方法与常见错法见 `references/05-perfect.md`、`08-sse.md`、`09-billing.md`、`10-cache.md`。

## 贯穿全程：运维面（长任务不看着就是白跑）

- 超过 60 秒的活儿一律后台跑，拿 job id 记在案
- 每 10 秒看一次日志，不是跑完才看
- 每条请求一行结构化日志：`rid/proto/node/status/ttft/三数 token/err`
- 四块看板：吞吐、延迟(p95 TTFT)、错误分桶、成本与命中率
- 四个立刻停手信号：401 占多数 / 429 集中 / 全部静默超时（先查余额）/ 同一 rid 出现两次
- 细节见 `references/07-ops-log.md`

## 铁律（跨阶段）

1. **先证伪再动手**：任何"应该能通"的判断，必须有 200/403 的实际响应作证。
2. **失败要分类**：`401` 是凭证、`403` 是权限/计划、`404` 是模型名或路由、`400` 是参数、`429` 是限流、`5xx` 是上游。**不同类别的处置完全不同，不许混为一谈。**
3. **一次只改一个变量**：同时改探针模型和 builder 模型，出问题无法归因。
4. **凭证与数据分离**：数据库里存 token 的文件不要进代码仓和发布包。
5. **任何"批量"操作都要有节奏控制**：平台的风控阈值远低于你的脚本速度。
6. **可观测性先行**：没有指标就没有优化，先把数字打出来再谈调优。

## 反面清单（这些做法 100% 会浪费时间）

- 直接对 `/v1/chat/completions` 硬编码上游模型名 → 平台一改就全崩
- 用"最强模型"做健康探针 → 一限制计划，所有节点被判死
- 把 `prompt_tokens` 当"未命中"统计 → 命中率算出 >100%
- 用进程内存存统计 → 每次重启面板归零
- 只测非流式就宣布完成 → 客户端全是流式，上线即空包
- 在没有抓包证据时猜字段名 → 猜错的成本是几十次 400
