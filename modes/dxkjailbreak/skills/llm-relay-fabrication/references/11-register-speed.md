# 11 · 注册机提速：先找瓶颈，再谈并发

> 注册速度慢，**90% 的时间不在你的代码里**，在"等邮件"和"被人机验证"。
> 先量一遍再优化，否则加并发只是把封号提前。

## 一、先分段计时（不做这步就是在猜）

单次注册拆成五段，每段打点：

```python
t = {}
t["prep"]   = 取邮箱 + 选域名 + 选代理
t["submit"] = 提交注册表单（含人机验证）
t["mail"]   = 邮件到达等待（0–30s 不等）
t["code"]   = 收码 → 提交验证码
t["login"]  = 重新登录换 token（**必须有，否则后续 401**）
t["init"]   = 建项目/沙箱并跑一次真实对话（很多平台必须）
```

**典型分布**（实测口径）：

| 段 | 耗时 | 占比 | 能不能优化 |
|---|---|---|---|
| prep | 0.2–1s | 3% | 预热能压到 0.05s |
| submit | 1–3s | 10% | 有限（含人机） |
| **mail** | **8–15s** | **60–70%** | **能（并发重叠，见下）** |
| code | 0.3s | 2% | 已够快 |
| login | 1–2s | 8% | 可与下一单重叠 |
| init | 15–25s | 15% | **能（后置异步 / 预建池）** |

结论：**不优化 mail 与 init，加并发毫无意义**。

## 二、提速的六个动作（按收益排序）

### 动作 1：把"等邮件"从串行变重叠（收益最大）

```python
# 错：一单一单等
for acct in batch:
    submit(acct); code = wait_mail(acct, timeout=30); verify(acct, code)

# 对：提交全部 → 统一收码（同一时间窗内等）
submitted = [submit(a) for a in batch]        # 提交是快的
codes = wait_mails_parallel(submitted, timeout=45)   # 并发轮询，5s 一次
for acct, code in zip(submitted, codes): verify(acct, code)
```

**收益**：10 单从 10×12s=120s 压到 ~15s，**时间除以批大小**。

**上限**：批大小不能超过风控容忍度。单 IP 一批建议 **3–5 单**，且批间 sleep 30–60s。

### 动作 2：邮箱池预热（把 prep 与 mail 都压掉）

```python
# 预建 2 倍于批量的空信箱，注册时直接领
POOL = [create_mailbox() for _ in range(20)]      # 后台常驻，用完补
def take(): return POOL.pop()
```

同时**多域名轮换**：`a.com / b.com / c.net` 三个收件域轮着用。单域被拉黑就全废（真实事故）。

**收码轮询间隔**：5s。低于 3s 是白耗配额，高于 10s 平均多等 3s。

### 动作 3：把 init（建项目/跑首轮）挪出关键路径

```python
# 方案 A：后置异步（注册成功即入池 pending，后台把它跑热）
pool.append({"status": "cold", "token": tok})
warm_queue.put(acct)          # 后台 worker 建项目 + 跑一次真实对话
# 方案 B：预建 3 个"热"项目轮换用（注意：闲置会被服务端回收，别建太多）
```

**注意**：有的平台"纯 API 建的空项目"能建会话但对话超时（schema 未初始化），必须真的跑过一次 AI 对话才算热。别省这一步。

### 动作 4：login 与下一单重叠

```python
# 上一单在 verify 的同时，下一单的 submit 就可以发
asyncio.create_task(submit(next_acct))
```

### 动作 5：代理预热 + 每 IP 一单

```python
# 代理建立连接本身要 0.3–1s，池子要预热（提前建好 TCP/握手）
proxy = pool.get(geo="US", sticky=False)
await proxy.warmup()          # 提前握手，注册时才不会卡这一秒
```

**单 IP 一单**是红线：同 IP 快速多单 = 按批次封（R-08）。

### 动作 6：人机验证只在真需要时才过

```python
probe = submit_form(dry_run=True)      # 先判：这个平台这一步要不要 Turnstile/滑块
if probe.needs_captcha:
    tok = turnstile.render_solve(...)  # 只在需要时起浏览器
```

**别每单都起浏览器**：Turnstile 一次 3–10s，起浏览器本身 2–5s，这是最大的隐性成本。有 token 缓存/复用方案就先复用（注意一次性、5 分钟有效）。

## 三、并发模型：小并发 + 强退避

```
并发度：
  单 IP        1 单在飞
  总并发       3–5（不是 42，实测 42 并发直接全灭）
失败处理：
  单次失败     sleep 60s 后重试，最多 3 次
  连续 3 单失败 → 停批，查是不是域名/IP/验证码变了
  401/403        → 立刻停，不是网络问题
```

**为什么小并发**：注册和业务 API 共享同一风控账本。你省下的 30 秒，可能换来整批 200 个号当天全废。

## 四、可观测（提速的前提是看得见）

```
每批一行：
batch=7 ok=6 fail=1 rate=6/95s  prep=0.1s submit=2.1s mail=9.8s code=0.3s login=1.4s init=□
```

- `init=□` 表示走了后置异步（关键路径不含 init）
- **速率口径统一为"每分钟成功数"**，别用"每单耗时"（批量重叠时没意义）
- 失败原因分桶：`mail_timeout / captcha_fail / ip_block / dup_email / platform_5xx`

## 五、提速的天花板在哪

| 手段 | 单机上限估计 | 再往上靠什么 |
|---|---|---|
| 邮件重叠 | 8–12 单/分钟 | 已接近平台提交速率上限 |
| 邮箱池 + 多域 | 15–20 单/分钟 | 需要更多收件域 |
| 多 IP 并行 | 20–40 单/分钟 | 住宅代理池规模 |
| 多机分片 | 线性 | 每机独立 IP/域名配额 |

**别追极限**：平台注册速率上限是**风控阈值**，不是技术上限。跑到阈值附近，账号存活率会断崖下跌。**要的是"能用的号/小时"，不是"注册成功的号/分钟"**。

## 六、和反代的衔接

注册出来的号进入池子后，反代侧要用它：

```
注册 → 重新 login 换 token → 建项目/沙箱（或后置异步）→ 跑一次真实对话验活
     → 写入 accounts.jsonl → 反代侧 worker 池轮换
```

**上线前逐个实测**：轮换到不可用账号会让 3/4 请求超时，比单账号更糟（实测 4 账号轮换 = 1 成功 3 超时 → 回退单账号）。

## 七、自检

```
□ 五段计时打点齐全（prep/submit/mail/code/login/init）
□ 邮件是批量并发等，不是串行等
□ 邮箱池预热 ≥ 2×批大小，多域名轮换
□ init 走后置异步或预建热项目
□ 单 IP 一单，总并发 3–5，失败退避 60s
□ 人机验证只在需要时起浏览器
□ 速率口径 = 每 N 分钟成功数
□ 注册后一定重新 login 换 token
□ 入池前跑过一次真实对话验活
```
